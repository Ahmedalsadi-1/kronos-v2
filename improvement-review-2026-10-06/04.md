# 04 - Browser isolation

Read-only review of `emain/preload-webview.ts`, `frontend/app/view/webview/`, and adjacent attachment/session enforcement. Read `emain/AGENTS.md` and `frontend/app/view/AGENTS.md`. No builds or tests run; no product code changed.

Existing strengths: `emain/emain-webview-policy.ts:54-72` strips unapproved preloads and forces context isolation, no Node integration, web security, and no nested webviews. `emain/emain-tabview.ts:318-325` denies guest-created native windows while forwarding popup intent to the host. The JSX `allowpopups` attribute therefore is not, by itself, evidence of unrestricted popup windows.

## P1 - Own remote-session permissions in main

Observed gap: no `setPermissionRequestHandler` or `setPermissionCheckHandler` registration found anywhere under `emain/`. Browser partitions originate in renderer metadata (`frontend/app/view/webview/webview.tsx:1349-1351,1756`); the attachment policy only excludes plugin prefixes (`emain/emain-webview-policy.ts:49-52`). Electron requires application permission policy for sessions serving remote content. Actual camera, clipboard, or screen exposure has not been demonstrated; OS and Chromium gates also affect results.

Recommendation: initialize both permission handlers once per remote session before first navigation. Deny unknown permission types, evaluate requesting frame origin rather than only top-level URL, and scope explicit grants to browser profile plus origin. Include worker checks where WebContents is null. Retain deliberate camera/microphone or screen sharing flows through a user-visible grant mechanism.

Acceptance: permission checks and requests deny unknown types; cross-origin iframe cannot inherit its parent's grant; private/profile grants do not bleed; navigation revokes temporary grants; legitimate explicitly granted conferencing still works.

Transferable upstream pattern: [Electron session permission callbacks and frame details](https://github.com/electron/electron/blob/main/docs/api/session.md#sessetpermissionrequesthandlerhandler), [official security recommendations](https://github.com/electron/electron/blob/main/docs/tutorial/security.md). Both verified live; session documentation explicitly requires both handlers. Use APIs available in the installed Electron 41 line rather than copying newer permission enum lists blindly.

## P2 - Enforce sandbox and a browser partition boundary at attachment

Observed policy weakness: `emain/emain-webview-policy.ts:66-72` sets isolation flags but never forces `sandbox=true`; explicitly supplied `sandbox=false` is therefore not overwritten. This is a missing invariant, not proof the normal guest is unsandboxed (Electron defaults normally enable sandbox). Empty partition falls through to the default session (`frontend/app/view/webview/webview.tsx:1351`); arbitrary non-plugin partitions remain accepted.

Recommendation: force sandbox for remote guests, and resolve browser sessions through a main-owned profile registry. Give ordinary browser content a dedicated default browser partition; reserve app/privileged partitions, with a controlled migration of existing cookies and documented private-session semantics. Avoid a broad WebContentsView rewrite for this improvement.

Acceptance: adversarial attachment preferences with `sandbox:false` become sandboxed; unknown/privileged partition claims fail; two intentional same-profile browsers share login, separate profiles and private sessions do not; automation preload and image menu continue operating in sandbox.

Transferable upstream pattern: [Electron attachment validation and sandbox guidance](https://github.com/electron/electron/blob/main/docs/tutorial/security.md), [partition semantics](https://github.com/electron/electron/blob/main/docs/api/session.md#sessionfrompartitionpartition-options). No runtime exploit demonstrated or migration tested.

## Upstream adoption, maintenance, licensing, and fit

Electron is already adopted locally (`package.json:49`, `^41.0.2`), so these recommendations require no added library. Its [release page](https://github.com/electron/electron/releases) was verified and shows ongoing release activity; repository page shows substantial forks and active pull requests. These are framework-maintained security patterns, not an unmaintained third-party browser fork.
