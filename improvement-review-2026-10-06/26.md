# 26. File content preview loading

**Priority: P2. Make Refresh reload streaming previews.**

Observed source defect: `/Users/albsheralsadi/kronterm/frontend/app/view/preview/preview-streaming.tsx:51` installs a Refresh callback that increments `model.refreshVersion`. However, this component never reads that atom. Its media URL at line 64 depends only on connection and file path, and its image, audio, video, and PDF elements receive that unchanged URL. `/Users/albsheralsadi/kronterm/frontend/app/view/preview/preview-model.tsx:438` reads the version only in the full-file atom used for text content; `statFile` at line 408 also has no refresh dependency. Header Refresh actions invoke this callback at model lines 353, 368, and 378. Thus the streaming refresh action has no dependency connecting it to the displayed document.

User-facing hypothesis: overwrite an image or PDF at the same path, click Refresh, and the previously loaded content remains visible until navigation or another actual resource reload. This was established by dependency inspection, not an Electron reproduction. Browser caching may amplify the symptom; no claim is made that every media format caches identically. Directory browsing was excluded. Standalone Vite preview configuration and Markdown/text loading were sampled; no additional high-confidence isolation finding is claimed.

Acceptance criteria:

- Refresh causes a new resource request for image, PDF, audio, and video previews at an unchanged path, including remote connections.
- File metadata is refreshed when replacement changes MIME type or size, so the view can switch to the correct renderer.
- Unrelated workspace renders do not reload media. Define whether explicit Refresh resets zoom/playback and keep that behavior consistent.
- Failed replacement requests show a recoverable error rather than silently retaining stale content.

Implementation fit: subscribe streaming preview to the existing refresh atom and include a monotonically changing revision in its URL, or implement explicit element reloads with equivalent cache invalidation. Re-fetch metadata through the same refresh boundary. This is a small local fix with no new package required.

Primary implementation reference verified by browsing: [React DOM resource property handling](https://github.com/react/react/blob/main/packages/react-dom-bindings/src/client/ReactDOMComponent.js). Use the existing React implementation rather than a custom PDF renderer merely to address reload behavior. [Mozilla PDF.js](https://github.com/mozilla/pdf.js) was also verified as an established Apache-2.0 PDF renderer with its own tests, but adoption would add worker packaging and update obligations without fixing image/audio/video refresh; it is not recommended for this defect. React is MIT; no source copying is required.

Test gate: a focused component test should invoke the registered callback and assert changed media URL plus unchanged path/connection. A browser integration fixture should serve two distinct same-path images and PDFs, overwrite between requests, and verify new rendered content after Refresh. Include remote URL formatting and failed reload recovery. No builds, tests, or product edits were performed in this review.
