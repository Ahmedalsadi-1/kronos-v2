# 47. Build and release: validate the shipped runtime

Priority: P1. Add a target-aware packaged-artifact gate before staging upload and release promotion. The strongest concrete finding is a Windows filename inconsistency: `scripts/validate-kronoscode-artifact.mjs:10-13` requires `bin/kronoscode.exe` on Windows, while `electron-builder.config.cjs:75-78` includes only `bin/kronoscode`. A successful source-directory preflight therefore does not demonstrate that the Windows package contains the executable the runtime needs. This is an observed mismatch; actual omission in a produced installer remains a hypothesis because this review did not build or unpack an installer.

The sampled path is `Taskfile.yml:124-133`: validate source artifact, build production frontend, then invoke electron-builder. The release matrix calls that task (`.github/workflows/build-helper.yml:127-150`). Existing build-output checks are useful: `scripts/check-build-output.mjs:29-38` requires MCP and Hermes plugin output files. However, these checks inspect the build directory rather than the application after electron-builder has applied resource filters. `electron-builder.config.cjs:50-89` carries several independently filtered runtime resources. At the promotion boundary, `.github/workflows/publish-release.yml:20-25` runs the staging-to-release task; the sampled publish job has no packaged-runtime verification step.

Use the existing electron-builder dependency and adopt its upstream testing pattern, rather than replacing the release system. Its [packTester helper](https://github.com/electron-userland/electron-builder/blob/master/test/src/helpers/packTester.ts) exposes packed-context assertions and ASAR verification. That is a directly applicable, established upstream example for inspecting the actual packaged file tree. The repository's [MIT license](https://github.com/electron-userland/electron-builder/blob/master/LICENSE) permits adaptation with retained notices. Upstream master changes over time: pin a reviewed commit when implementing; this review verifies the source pattern, not a particular test suite's execution.

Plan: first make executable filters platform-aware; second generate a required-resource manifest for each supported OS/architecture and validate the unpacked application, including executable permissions and binary architecture; third run short packaged startup checks for backend and agent processes with an isolated profile; finally require the resulting manifest, checksums, and successful smoke result before promotion. Preserve compatibility identifiers and existing update URLs until ownership is separately confirmed.

Acceptance gate: deleting the packaged agent or replacing it with the wrong architecture must fail validation; Windows must contain the `.exe`; macOS and Linux executables must retain execute permissions; a clean-profile launch must report backend and agent readiness. No builds or product edits were performed.
