# 08 — Electron tool server

## P2 — Bound and explicitly own MCP sessions

Observed: `emain/kronterm-tool-server.ts:251-272` connects a fresh MCP server/transport; `:307` does so for every authorized request lacking a session ID, including GET/DELETE. Sessions are retained at `:255` until transport close (`:261-262`); there is no capacity limit, idle expiry, caller removal, or server stop method in this class. Startup also creates an unused transport (`:224`). A reconnecting client that initializes new sessions without DELETE can accumulate retained transports throughout the Electron process lifetime. Memory impact is a hypothesis, not measured in this read-only review.

Recommendation: create transports only for valid POST initialize requests, remove the unused startup transport, cap sessions per caller and globally, and expire idle sessions while protecting active requests/SSE. Own both server and transport disposal; revoke caller tokens and close their sessions when the owning runtime ends.

Acceptance: sessionless GET/DELETE and malformed POST create zero transports; repeated initialization reaches a documented cap; idle abandoned sessions close; active SSE/tool calls survive idle sweeps; caller disposal invalidates its token/session while other callers continue; shutdown closes all transports and listener.

Upstream model: the [official TypeScript SDK example](https://github.com/modelcontextprotocol/typescript-sdk/blob/v1.x/src/examples/server/simpleStreamableHttp.ts#L651-L737) implements idle tracking, capacity rejection, initialization-only creation, and [shutdown cleanup](https://github.com/modelcontextprotocol/typescript-sdk/blob/v1.x/src/examples/server/simpleStreamableHttp.ts#L835-L850). Adapt its lifecycle pattern without copying OAuth/demo logging.

## P2 — Catch the entire HTTP dispatch

Observed: `:225-226` discards the promise from `handleRequest`; caller providers (`:292`, `:309`) and transport creation (`:307`) can throw outside the MCP try block. Resulting unhandled rejection/socket behavior depends on runtime policy and is untested.

Recommendation: catch dispatch at the HTTP callback boundary, return a generic 500 only before headers are sent, and terminate an already-started response safely. Acceptance: injected provider/connect failures yield no unhandled rejection and no hanging response; error detail stays in local diagnostics. The upstream example's error handling checks `res.headersSent` before writing a response (`:743-752`).
