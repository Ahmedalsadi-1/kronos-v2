# Review 29/50: Sandbox lifecycle ownership

## Priority and evidence

**P1: Bind asynchronous work to a session instance before allowing same-name restart.** Scope: `pkg/sandbox/manager/sandbox.go`; root `AGENTS.md` applies because there is no sandbox-specific or `pkg/AGENTS.md`. This was a read-only source review; no build, test execution, runtime launch, or product edit occurred.

Observed: `Stop` kills a QEMU process and removes its map entry without joining its exit waiter (`sandbox.go:560-565`). `waitForExit` subsequently finds whichever session currently occupies the same name and either changes its status/process or deletes it (`sandbox.go:499-510`). A newly started session can therefore be modified by the old process's completion. This is a concrete permitted interleaving, not a reproduced runtime failure. Consequence: replacement session disappears or becomes `error` with `Process=nil`, preventing normal management of a still-live process.

The default desktop runtime has the same ownership gap without needing QEMU: its readiness context is detached and never stored for cancellation (`sandbox.go:401-405`); `Stop` deletes the entry (`sandbox.go:544-547`); old readiness success or timeout acts on the replacement name (`sandbox.go:428-445`, `516-525`). Mutexes prevent simultaneous map access but do not distinguish generations. Concurrent starts also check existence before launching outside the lock (`sandbox.go:195-214`, `268-280`), then overwrite the entry; duplicate processes are a related hypothesis requiring a deterministic regression test.

## Proposed improvement and acceptance gate

Give each creation an immutable generation/token and owned cancellation function. Reserve the starting session atomically. Every readiness, error, exit, and stop transition must compare the captured instance with the current entry under the mutex. Cancel and join owned work when stopping, with bounded subprocess cancellation; do not hold the mutex during process waits.

Acceptance criteria: barrier-controlled tests stop session A, install B with the same ID, then release A's success, failure, and exit callbacks. B's status, process, and membership must remain unchanged. Parallel same-ID starts must launch at most one process. Cancellation must stop polling promptly, including a stalled Docker CLI. Run `go test -race ./pkg/sandbox/...` as the implementation gate; never `go build`. Existing `sandbox_test.go` checks runtime selection and Docker arguments, but has no lifecycle coverage.

## Verified upstream reference and fit

[Coder agent implementation](https://github.com/coder/coder/blob/main/agent/agent.go) provides a directly relevant ownership pattern: `Close` cancels the agent's hard context and waits on `closeWaitGroup`; metadata reporting cancels its child context and joins its collector/ticker channels. These were verified in [raw source](https://raw.githubusercontent.com/coder/coder/main/agent/agent.go). Adapt those principles, rather than importing Coder's server stack. [Repository](https://github.com/coder/coder) shows approximately 16.9k stars and 1.6k forks, and an existing [agent test suite](https://github.com/coder/coder/blob/main/agent/agent_test.go): adoption/maintenance indicators, not proof of matching lifecycle guarantees. Release cadence and upstream CI execution were unverified. Its [AGPL-3.0 license](https://github.com/coder/coder/blob/main/LICENSE) makes direct code reuse a licensing review item; KronTerm compatibility is unverified. An independent Go implementation adds little dependency maintenance.
