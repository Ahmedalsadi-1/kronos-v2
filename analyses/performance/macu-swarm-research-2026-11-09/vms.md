# Cua as optional VM infrastructure for the MACU swarm

Reviewed local working-tree source over KronTerm HEAD `1e66fbb9aa71b275203bc941f61094e6d1ee0b85` and an upstream shallow checkout of Cua `6285c481d2d867eb954a6e6c5531ba8a88182832`. Static review only. No runtime launched, dependencies installed, or benchmark numbers collected.

## Source-verified findings and reuse

1. **Existing execution path covers the first integration.** `emain/linux-desktop/qemu-linux-runtime.ts` runs one ARM64 Ubuntu VM under HVF. `qemu-provision.ts` configures two vCPUs and 2 GiB RAM. The sparse disk is 20 GB, and the pinned CUA Driver 0.20.0 already runs inside the guest over authenticated loopback SSH. MACU can issue typed operations against this existing path once the coordinator binds a worker to a granted computer. The singleton directory, SSH port, control generation and queue in `QemuLinuxRuntime` are the scale-out seam. For a first swarm, workers can run independently and serialize desktop input for a shared target. To support concurrent computer actions, give each worker a distinct VM with isolated disk, host key, control and viewer endpoints. Linux is for Linux/browser tasks. `emain/macos-vm-runtime.ts` uses Tart for local macOS Labs VMs and exposes an owner-scoped VNC viewer, with readiness based on a VNC endpoint announcement. It does not expose the Linux-style agent lease or guest command protocol. Reuse Tart for evaluation of actual macOS workloads first. Add Lume only if measured requirements justify a separate provider.

2. **Lease fencing stays with KronOS.** QEMU checks assignment, owner and generation before enqueue and again at dispatch, checks cancellation, limits the queue to 16, and deduplicates screenshots only across compatible ordering. The task registry in `emain/sandbox-task-runtime.ts` serializes operations for a desktop, handles retry/partial start cleanup, and preserves a human-taken-over machine. Existing workflow tool scoping in `emain/kronterm-native-tool-bridge.ts` checks computer ID and workflow identity. The sandbox skill explicitly describes reservation IDs as grants behind a shared bridge rather than authenticated worker identities. Bind the grant to authenticated coordinator worker/session context and an incarnation-specific generation. Revoke channels and reject old frames/queued inputs after takeover, cancellation, stop or reuse. A fence before dispatch cannot retract an already-dispatched guest command, so teardown needs bounded drain/abort before reassignment. QEMU currently signals SIGTERM and closes its viewer on stop. Treat observed process exit and cleanup as prerequisites to replenishment, and quarantine failed cleanup. Tart already waits for exit with SIGKILL escalation and tears down sockets on process exit or owner close.

3. **Warm-pool mechanism worth adapting as a design.** Cua's `libs/cua/crates/cua-daemon/src/pool/mod.rs` indexes by backend and compatible image/resources/ports/probes/environment, separates Space identity from pool templates, removes a ready member before the asynchronous claim, and rotates the guest token with a per-member secret. Failed claim cleanup goes to a cold path. `pool/named.rs` separates identity from shape. `prewarm_pools.rs` carries readiness in the shape, targets a finite ready count, and provides TTL. The policy also observes memory and host conditions. Start with one bounded warm slot keyed by immutable image digest, guest type, resources and required capabilities. Use per-run overlays/identity and no user login state in the pool. Budget warm plus active instances by CPU, RAM and actual allocated disk bytes, reserve foreground headroom, and bound concurrent boots and refill. Prefer deleting a consumed worker VM after exporting task artifacts over putting the active guest back in the pool.

4. **Separate disk clone from saved-memory restore.** Lume `libs/lume/src/FileSystem/Home.swift` pairs macOS disk with auxiliary boot storage. APFS clonefile covers the disk and optionally saved state, with full-copy fallback. Ordinary clone assigns a fresh MAC. Saved state retains its MAC and machine identifier, so `libs/cua/crates/cua-vmm/src/lume/mod.rs` prepares separate macOS warm states with distinct addresses. It boots a temporary clone to probes, settles, saves, clones into place, and uses bootstrap identity before token initialization. Resume waits for saved-state consumption before checking probes. That code currently assumes two macOS warm state identities. Confirm applicable guest limits separately before implementation. Keep a prepared Linux disk overlay or cold/prewarmed guest as the baseline. Only pursue saved memory after testing host/guest compatibility, unique identity, resumed guest clocks, known-hosts identity, restore failure cleanup and cold fallback. Cross-volume full copies and retained memory snapshots have different disk and latency costs from CoW clones.

5. **Verify readiness at the action layer and keep observation bounded.** QEMU runs cloud-init readiness and a driver status check over SSH, tracks health by PID with a 15-second cache, and validates PNG completeness. Its separate VNC bridge disables WebSocket compression and applies backpressure. Tart's bridge is single-viewer, loopback, token and origin checked, with backpressure. An announced VNC endpoint is a transport milestone. A MACU worker should wait for the first usable frame and a guest/app capability probe, within a startup deadline. Model calls can use on-demand frames. The Linux screenshot path writes PNG in the guest, base64-encodes it over SSH and returns a data URL. Measure each copy and encoding stage before switching transport. Keep live viewers opt-in per VM and measure throughput with multiple active workers, with and without viewers.

## Verification proposal

- Extend the existing focused tests `emain/linux-desktop/qemu-linux-runtime.test.ts`, `qemu-vnc-bridge.test.ts`, `emain/sandbox-task-runtime.test.ts` and `emain/macos-vm-runtime.test.ts`. Cover two claims racing for one warm member, old generation and frame rejection after reuse, unrelated VM isolation, takeover with queued input, partial boot and stop timeout, daemon restart reconciliation, identity rotation failure, and preservation of human-owned sessions. Existing tests already exercise handback fencing, screenshot ordering, cancelled queued inputs, PID-bound readiness, scoped VNC teardown and partial-start cleanup.
- Instrument request, capacity admission, clone, spawn/resume, guest handshake, first validated frame, first verified input and teardown. Compare prepared cold boot, warm claim, and saved-state resume only where implemented. Record p50/p95, timeout/failure rates, CPU/RSS, allocated disk, screenshot bytes and input-to-visible latency on the same host/image. Report idle and burst cases, including queue delay and tests with a viewer open. Upstream `libs/cua/crates/cua-daemon/tests/warm_pools_live.rs` supplies a timing schema for an opt-in **container** benchmark, and `libs/cua/crates/cua-vmm/examples/lume_warm.rs` measures state preparation. Neither measures KronOS nor establishes its expected speedup.
