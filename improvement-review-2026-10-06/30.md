# Review 30: wsh CLI secret input

Scope: read-only sampling of `cmd/wsh/cmd/wshcmd-root.go`, `wshcmd-file.go`, and `wshcmd-secret.go`; nearest applicable instructions were `cmd/AGENTS.md`. No product edits, tests, or builds were performed.

## Priority P1: provide secret input outside argv

Observed: `/Users/albsheralsadi/kronterm/cmd/wsh/cmd/wshcmd-secret.go:36` advertises `set [name]=[value]`, requires one argument, and `/Users/albsheralsadi/kronterm/cmd/wsh/cmd/wshcmd-secret.go:107` rejects an argument without `=`. The value is extracted directly from that argument at line 113. There is no stdin or hidden-prompt input branch in this handler. Consequently, the available CLI interface puts a supplied secret in the process argument vector. A literal typed value can also enter shell history. Whether another process can inspect it depends on OS privileges; actual disclosure was not reproduced. Backend keychain protection does not address this input exposure.

Recommendation: support `wsh secret set NAME` using redirected stdin, and a hidden terminal prompt when interactive. Keep the existing assignment syntax for compatibility, but document stdin/prompt as the preferred route. Existing `WrappedStdin` at `wshcmd-root.go:33` provides an injectable starting point. Define size limits and newline handling explicitly, and avoid printing values in success or error output.

Acceptance criteria: command tests inject stdin containing spaces, equals signs, Unicode, empty input, and multiline values; verify the chosen trailing-newline policy. Interactive input must not echo the secret. Input errors and cancellation must not invoke the write RPC. Tests capture both output streams and assert absence of a sentinel secret. Invalid names must fail before RPC; the setter currently only rejects empty names at line 115 while get/delete apply the shared regex. Retain the existing storage-backend rejection.
