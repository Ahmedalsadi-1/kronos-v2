# 02 - Window lifecycle

Scope: `emain/emain-window.ts`; nearest instructions read: `emain/AGENTS.md`. Read-only inspection; no builds or code changes. Online primary sources checked 2026-10-06.

## Recommendations

1. **P1 - Preserve mutations in the window action queue. Observed logic defect, runtime impact untested.** `emain/emain-window.ts:534` replaces any pending action with the newest entry, including `createtab` and `closetab`; these actions are not interchangeable navigation intents. A third action can silently discard a requested tab creation/deletion while one action is awaiting RPC. Queued callers also return immediately at `:536`, rather than waiting for execution. Separate FIFO mutations from coalescible tab selection and return a completion promise per command. Proven reference: [VS Code Queue and LimitedQueue](https://github.com/microsoft/vscode/blob/main/src/vs/base/common/async.ts) explicitly distinguish serial execution from replacement of a pending task. Acceptance: hold the first RPC pending, enqueue create/close/switch, release it, and verify every mutation executes exactly once in order; switch coalescing has an explicit cancellation/completion outcome; one failure does not strand later commands.

2. **P1 - Run resource disposal independently of quit/update persistence policy. Observed cleanup omission; shutdown leak/crash impact is a hypothesis.** `emain/emain-window.ts:323` returns before map removal and child disposal when quitting/installing. `:348` closes tab views on the normal path, and `emain/emain-tabview.ts:227` already closes their webContents correctly. Move unconditional idempotent cleanup before policy branches; keep backend deletion conditional. [Electron BaseWindow ownership documentation](https://github.com/electron/electron/blob/main/docs/api/base-window.md) requires explicit child webContents closure; [Electron BrowserWindow implementation](https://github.com/electron/electron/blob/main/lib/browser/api/browser-window.ts) provides the established contrast. Acceptance: normal close, relaunch, updater install, and quit all clear window ownership and close each child once; backend persisted window deletion follows existing save settings; repeated cleanup is safe.

3. **P2 - Own delayed work and cancel it on disposal. Observed missing cancellation/guards; race failures need reproduction.** Refocus callbacks `emain/emain-window.ts:470` and `:475` call webContents without a destroyed check; deferred removal at `:545` reaches `contentView.removeChildView` at `:658` after window close. The bounds poller `:222` self-clears only on its next tick. Adopt a small per-window disposal registry and a lifecycle generation/abort guard after asynchronous initialization (`:400`) before view mutation. [VS Code DisposableStore/toDisposable](https://github.com/microsoft/vscode/blob/main/src/vs/base/common/lifecycle.ts) is a concrete model for idempotent resource ownership. Acceptance: close during pending init/refocus/removal; advance timers; no Electron calls against destroyed owners, no unhandled exceptions, and no remaining timers/views.

## Upstream credibility and adoption caveats

[Microsoft VS Code](https://github.com/microsoft/vscode) is an established Electron editor; opened upstream source includes current Queue/LimitedQueue and DisposableStore implementations, and [main-process app.ts](https://github.com/microsoft/vscode/blob/main/src/vs/code/electron-main/app.ts) uses DisposableStore. [Electron](https://github.com/electron/electron) is KronTerm's existing desktop framework; its current source and ownership documentation directly apply. Search indices showed source refreshes within days/weeks, which verifies accessible current implementations but is not a precise last-commit measurement. No popularity counts are needed to justify these specific patterns.
