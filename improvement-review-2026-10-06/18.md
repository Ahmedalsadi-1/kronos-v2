# Review 18: Jotai state cache lifetime

Scope: read-only sample of `frontend/app/store`, including nearest `AGENTS.md`, `jotaiStore.ts`, `global-atoms.ts`, `global.ts`, `tab-model.ts`, `connections-model.ts`, and the existing global-atoms test. No builds or product edits performed.

## Priority: P2 - release caches for permanently deleted objects

Observed: `frontend/app/store/tab-model.ts:14` declares a module-level strong `Map<string, TabModel>`. Its accessor at lines 53-60 inserts every previously unseen real tab ID. Each retained model owns atom configurations and another metadata-atom map (lines 20-23, 40-47). A frontend-wide search for `tabModelCache` found only its declaration, lookup, and insertion; there is no deletion or reset path.

The same pattern appears at `frontend/app/store/global-atoms.ts:12` and `frontend/app/store/global.ts:274-280`: `orefAtomCache` retains per-object maps, including block and connection entries. A frontend-wide reference search found no eviction. Cached block atoms capture block IDs (`global.ts:286-295`). `frontend/app/store/wos.ts:263` already processes authoritative delete updates, providing a concrete lifecycle event to investigate for cleanup integration.

Hypothesis: a renderer that repeatedly creates and permanently deletes unique tabs or blocks retains obsolete models and atom configurations for its entire lifetime. The strong-reference retention is visible in source; growing renderer memory, duration of relevant renderers, and practical user impact were not measured. This is a bounded-window lifetime issue, not evidence of an application-wide leak across renderer restarts.

## Proven pattern and acceptance gate

[Jotai's official family documentation](https://jotai.org/docs/utilities/family) explicitly describes the analogous Map-backed atom cache retention problem and recommends removing unused parameters. Adopt explicit object-lifecycle eviction in the existing caches; replacing them with `atomFamily` alone would preserve the problem. Evict after confirmed permanent deletion, rather than ordinary tab switches or temporary unmounts, to preserve identity and retained tab state.

Acceptance criteria: a focused Vitest lifecycle test creates multiple unique IDs, confirms stable model/atom identity while live, delivers confirmed deletion, and verifies obsolete cache entries disappear while surviving IDs retain identity and values. Cover duplicate deletion and mock-environment isolation. Include a bounded repeated create/delete sequence so cache cardinality tracks live objects. Validate actual delete routing before adding cleanup; this review does not prove which caller owns that responsibility.
