## Proven upstream pattern and fit

[microsoft/vscode smoke-test instructions](https://github.com/microsoft/vscode/blob/main/test/smoke/README.md) document testing an explicit Electron build and matching smoke-test versions to the release under test. Adopt that architectural pattern: the test target must be the artifact built from the same commit, and fixtures own temporary resources. VS Code is a mature Electron application with terminals and remote workflows, making it a stronger comparison than generic browser-only tests. Its source is [MIT licensed](https://github.com/microsoft/vscode/blob/main/LICENSE.txt); preserve notices if copying code. Prefer adapting the pattern to KronTerm's own automation surface rather than importing VS Code's large driver stack. Existing TestDriver can remain exploratory coverage while deterministic assertions establish the gate.

## Plan and acceptance gate

First add a pull-request workflow for non-watch Vitest, TypeScript checking, and relevant Go tests; publish existing JUnit/LCOV even on failure. Then add isolated-profile packaged smoke cases for launch, terminal readiness, layout switching, persistence after restart, and a stubbed agent round trip. Start with one supported desktop runner, expand after stability evidence, and keep credentials out of fixtures.

Acceptance: an intentionally failing unit assertion blocks merge; a broken packaged entry point fails smoke; each failure retains redacted logs, screenshots and tested commit metadata. Establish a measured runtime/flakiness baseline before enforcing a new timing budget. No builds, tests or product edits were performed in this review.
