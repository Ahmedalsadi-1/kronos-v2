## Strongest finding: stream decoding loses Unicode (P1)

**Observed:** [acp-transport.ts:188](/Users/albsheralsadi/kronterm/emain/acp/acp-transport.ts:188) decodes each stdout Buffer separately with `toString("utf-8")`, then concatenates strings. A multibyte character split across OS pipe chunks becomes replacement characters before JSON parsing. The same pattern appears in stderr at line 209. Valid JSON can therefore deliver silently corrupted agent text, paths, or tool arguments. Production occurrence is a hypothesis; the decoding behavior is established by the source. The sampled test search did not reveal Unicode/chunk-boundary coverage.

**Improve:** retain bytes until a complete newline frame exists, then decode; alternatively use Node's stateful `StringDecoder` and flush at EOF. Preserve the existing compatibility handling for pretty-printed JSON separately.

**Acceptance:** emit one response containing Arabic, CJK, and emoji at every possible byte split; assert identical parsed content and no replacement characters. Cover multiple messages per chunk and final frame without newline. Stderr must preserve split multibyte characters too.

## Related improvement: bound incomplete stdout frames (P2)

**Observed:** [acp-transport.ts:187](/Users/albsheralsadi/kronterm/emain/acp/acp-transport.ts:187) grows `buffer` until newline without a limit. `MaxPendingJsonBytes` applies only after lines reach the multiline compatibility accumulator, and is a string-length check rather than byte count. Memory exhaustion from a noisy/malformed agent is a hypothesis, not a measured incident.

**Improve:** set an explicit byte limit for unfinished frames and a defined oversize policy, settling pending requests and reporting one transport failure when terminating. Avoid an arbitrarily small cap that rejects legitimate large tool output.

**Acceptance:** a repeated newline-free stream cannot grow retained memory beyond the configured allowance; oversized input produces one diagnostic and releases pending requests; ordinary large allowed frames still parse.

## Transferable upstream pattern and evidence

Microsoft's [vscode-languageserver-node repository](https://github.com/microsoft/vscode-languageserver-node) provides established JSON-RPC transport infrastructure used by VS Code language client/server packages. Its [ReadableStreamMessageReader source](https://github.com/microsoft/vscode-languageserver-node/blob/main/jsonrpc/src/common/messageReader.ts) appends raw byte chunks to a message buffer and reads a complete body before decoding; it also provides partial-message timeout signaling. This directly supports separating framing from decoding. The repository documents successive JSON-RPC 9.0.1/9.0.3 and client/server releases and approximately 1.8k stars, providing adoption and maintenance evidence, not proof of suitability for every ACP agent.

**Fit/license:** upstream uses Content-Length framing, whereas ACP here uses NDJSON; transplant the byte-buffering principle, not the wire format or whole dependency. Source is MIT; copied code requires its notice. The buffer cap is a local extension, not an upstream feature claimed by this review.
