# 25 - Editor/LSP: preserve byte framing

**Priority: P1 (editor correctness).** Replace the interactive language-server stdout string parser with a byte-oriented transport. This is a bounded reliability change in the Electron process; no renderer redesign is required.

## Evidence and scope

Observed in `/Users/albsheralsadi/kronterm/emain/emain-lsp.ts:393`: each stdout chunk is immediately decoded with `chunk.toString()` and appended to a JavaScript string. Lines 406-411 then compare and slice that string using the server's Content-Length. Content-Length describes encoded bytes, while JavaScript string length counts UTF-16 code units. A response containing non-ASCII hover text or diagnostic messages therefore has a different measured length. Decoding each arbitrary chunk also damages a UTF-8 character whose bytes straddle chunk boundaries. The outbound writer already measures bytes correctly at line 453. The separate agent-query transport keeps a Buffer and slices bytes before decoding at lines 151-170, providing a useful local contrast.

`/Users/albsheralsadi/kronterm/frontend/app/lsp/lsp-transport.ts:26-32` expects a complete JSON string and parses it immediately. Consequently, the main-process mismatch can stall delivery or combine the beginning of a later frame with a preceding body. This consequence follows from static code inspection; no live server failure was reproduced. I also sampled `lsp-service.ts` and `lsp-client-manager.ts`. Existing `emain/emain-lsp.test.ts` covers path containment and result bounding, rather than interactive stream framing. No product files were modified and no builds were run.

## Proposed adoption and verified upstream

Use the Node `StreamMessageReader` from [Microsoft's vscode-languageserver-node](https://github.com/microsoft/vscode-languageserver-node/blob/main/jsonrpc/src/node/main.ts), forwarding decoded messages through the existing session-specific IPC envelope. Its [common reader implementation](https://github.com/microsoft/vscode-languageserver-node/blob/main/jsonrpc/src/common/messageReader.ts) reads a complete byte body before decoding. These primary sources were browsed on 2026-10-06. KronTerm's renderer already imports vscode-jsonrpc, but verify the installed version's Node export and main-process bundler compatibility before adoption. Alternatively, extract the existing byte parser into one shared, tested helper.

The repository's [MIT license](https://github.com/microsoft/vscode-languageserver-node/blob/main/License.txt) fits this Apache-2.0 application with retained upstream notices. Prefer the maintained package API over copying upstream implementation; pin a compatible version and assign transport ownership to the Electron/LSP maintainer. Adoption effort is small to moderate, including cleanup/error wiring and dependency verification.

## Acceptance criteria and test gate

A mocked child stdout must deliver two consecutive responses exactly once when one contains accented characters, CJK, and emoji. Split the encoded frames at every possible byte boundary, including inside UTF-8 sequences and header delimiters; also test multiple frames in one chunk. Assert recovered objects equal the originals and that an incomplete final body remains pending until completed. Cover malformed JSON through the existing reader error path and dispose listeners on termination. Gate merging on focused Vitest transport tests and the repository TypeScript check; then smoke-test one supported server with a Unicode diagnostic or hover response.
