# Galaxy coordination reference for the MACU swarm

Read-only source comparison. Microsoft UFO checkout eae3c0a8d168c47cb10df0652e293e092eda1078, MIT (LICENSE:1–3). No runtime validation. Upstream references below are relative to that commit and local references are relative to KronOS.

## Platform boundary

Galaxy's CLI exposes windows, linux and mobile, with Windows as fallback for unrecognized host OS (ufo/client/client.py:57–72). The Windows GUI/app API stack is evidenced by ufo/automator/puppeteer.py:24 and ufo/module/sessions/session.py:42. Linux MCP implements command execution (ufo/client/mcp/http_servers/linux_mcp_server.py:749–828), and Linux Galaxy examples explicitly use a CLI executor (documents/docs/linux/as_galaxy_device.md:16–41). That path provides Linux shell capability, separate from Linux GUI. Mobile is a real ADB-based Android implementation with screenshot, UI tree and action tools (ufo/client/mcp/http_servers/mobile_mcp_server.py:5–11,259–385,413–482), irrespective of the broader platform-extension language. macOS is listed as coming soon (galaxy/README.md:598–614). No iOS adapter was established in the examined paths. KronOS already has Android and iOS simulator control paths (emain/computer-targets-runtime.ts:114–191,208–220,279ff.) and its own Linux VM GUI path (emain/linux-desktop/qemu-linux-runtime.ts:451–492). Existing Computer workflow execution independently requires a native macOS app (emain/computer-workflow-engine.ts:37–49). A control adapter existing elsewhere does not make it a workflow executor automatically.

## Integration requirements

1. **MACU owns decomposition and replanning.** Consume its versioned DAG as proposed steps, dependencies, required capabilities, and verification criteria. Keep durable execution authority in Electron using the existing workflow validation and journal (emain/workflow-store.ts:75–125,590–649). Galaxy's scheduler validates assignments, syncs edits and launches ready tasks, and limits editable tasks/dependencies to work that has not started (galaxy/constellation/orchestrator/orchestrator.py:394–429, galaxy/constellation/task_constellation.py:332–357). Apply MACU edits only to pending work, preserve running attempt identity and verified evidence, and validate graph revisions atomically.

2. **A capability registry must describe current scoped executability.** Galaxy separately tracks registration, capabilities, heartbeat and device status, refreshing system information after connection (galaxy/client/components/device_registry.py:29–63,154–170,198–225, galaxy/client/device_manager.py:265–297). Its strategy named capability_match actually tries preferred IDs, matches device_type and falls back to any available device (galaxy/constellation/orchestrator/constellation_manager.py:212–247). In KronOS intersect live adapter operations, target identity/control generation, and session/delegation grant. Model shell, GUI observation and GUI input separately. Missing capability or approval blocks dispatch. Recheck immediately at the existing scoped tool server rather than trusting planner-supplied IDs (emain/computer-access-policy.ts:142–155,205–228, emain/kronterm-tool-server.ts:688–729,750–766).

3. **Schedule readiness on state changes, with fenced per-resource claims.** Galaxy launches deduplicated futures per task ID and waits for FIRST_COMPLETED; its no-active-task branch sleeps briefly (galaxy/constellation/orchestrator/orchestrator.py:468–513). Its device manager uses a per-device queue and synchronous BUSY transition before its first await, an in-process admission pattern (galaxy/client/device_manager.py:594–635, galaxy/client/components/task_queue_manager.py:24–62). KronOS currently schedules one success-gated step per run and holds run-wide computer/workflow locks (emain/workflow-store.ts:598–632); workflow runtime uses a queue timer and drain (emain/workflow-runtime.ts:19–43,62–67). Claim ready steps on plan/verified-result/device/control events with bounded concurrency, serialize interactive steps per actual shared desktop/display, and recheck ownership before every action. Preserve existing native-desktop contention and takeover/generation checks (emain/workflow-store.ts:583–609, emain/computer-targets-runtime.ts:223–276). Treat an empty frontier as an explicit blocked/terminal diagnosis, including dependency failures and unavailable capability, with wake conditions for recoverable waits.

4. **Reconnect transport and reconcile effects independently.** Galaxy publishes disconnect, fails the active task and schedules one bounded reconnect loop per device (galaxy/client/device_manager.py:390–444,462–549). KronOS already restores active work as uncertain and requires resolution before restart (emain/workflow-store.ts:175–185,493–529). Persist per-attempt identity, dispatch/ack status and the target's control generation. Rediscovery refreshes eligibility. An unacknowledged or disconnected mutation may already have happened, so reconcile by readback or human review before reissuing it; allow retry automatically only when safe by contract. Preserve independent branch outcomes and expose explicit blocked-by-dependency/failed/uncertain distinctions.

5. **Verify results before releasing dependencies.** Galaxy correlates replies by session and receiving device, rejecting cross-device result injection (galaxy/client/components/connection_manager.py:294–334,415–485). It nevertheless defines success from worker status, evaluates dependency predicates on terminal result or error, and emits a final completed envelope with empty results even when stats carry the real outcome (galaxy/constellation/orchestrator/orchestrator.py:539–578,632–661, galaxy/constellation/task_constellation.py:1133–1156). In KronOS bind replies and evidence to run/step/attempt, assigned target and generation; reject late or wrong-target replies. Require scoped observations or typed artifact/command checks for each declared postcondition. Preserve the existing observation-ID/assigned-app safeguards and human review path (emain/computer-workflow-engine.ts:43–86, emain/workflow-runtime.ts:68–87,127–142). A worker summary is evidence to inspect. Release dependent nodes after verified success, or along an explicitly declared failure branch, and retain results in the journal.
