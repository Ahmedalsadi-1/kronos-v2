# Anti-slop audit 001: KronTerm non-canvas workspace

Date: 2026-09-02

Scope: The current working tree, focused on the `widgets`, `tabs`, `web`, and shared desktop workspace chrome. Canvas-specific styling is excluded except where a shared rule also affects non-canvas surfaces.

Mode: Audit first. No product code was changed.

Provisional design read for this audit: desktop developer workbench for technical operators, with a dense evidence-first KronTerm visual language, dial ENERGY 2 / RHYTHM 1 / MOTION 1. This is based on the product model in `AGENTS.md`; the repository has no root visual `DESIGN.md`, so it is not yet implementation direction.

## Findings

### 1. [HIGH] The supported preview path cannot render the current workspace

- Rule: R-35, verify before delivery.
- One-line reason: `task preview` exits after Vite cannot resolve `@hermes/plugin-sdk`, so the non-canvas UI cannot be visually exercised from the repository's documented preview target.
- Evidence: `Taskfile.yml:61-71` defines the preview target; `frontend/preview/vite.config.ts:11-43` has no alias for the plugin SDK; `frontend/hermes/plugins/kanban/drawer.tsx:29` imports the unresolved package.
- Observed command: `task preview` reached Vite and then failed with `@hermes/plugin-sdk` imported by `frontend/hermes/plugins/kanban/drawer.tsx` unresolved. It also reported missing embedded `kronoscoder/nanobrowser` tsconfig bases.
- Proposed fix boundary: restore the preview alias or exclude runtime-only plugin sources from preview dependency scanning, then make `task preview` and `task build:preview` clean enough to capture widgets and tabs at multiple window sizes.

### 2. [HIGH] Several non-canvas controls are pointer-only

- Rule: R-32, keyboard accessibility.
- One-line reason: widget group headers and tab split targets use clickable or droppable `div` elements without keyboard semantics or an equivalent keyboard command.
- Evidence: `frontend/app/workspace/widgets.tsx:713-745` renders both group-header variants as `div onClick`; `frontend/app/tab/widget-tabs-layout.tsx:552-577` renders split targets as drag-only `div` elements.
- Proposed fix boundary: use real buttons for folding, preserve the compact visuals, and add a keyboard-accessible move/split action for widget tabs instead of relying exclusively on drag and drop.

### 3. [HIGH] Empty and error states are visually indistinguishable

- Rule: R-27, complete UI states.
- One-line reason: app discovery failures are logged and converted into empty arrays, after which the user sees the same generic empty message as a valid no-apps result.
- Evidence: `frontend/app/workspace/widgets.tsx:300-329` logs rejected fetches but stores no error state; `frontend/app/workspace/widgets.tsx:441-450` only renders loading or generic empty results; `frontend/app/workspace/widgets.tsx:1113` says only `No matching widget`; `frontend/app/tab/tabcontent.tsx:501-504` offers no recovery action for a missing tab.
- Proposed fix boundary: model loading, empty, filtered-empty, and failure separately; name what failed; add Retry or the relevant next action; keep diagnostics out of console-only handling.

### 4. [MEDIUM] Agent activity stacks every attention effect at once

- Rules: R-13, glow dose cap; R-19, motion with purpose.
- One-line reason: one active widget can simultaneously show a five-layer rainbow glow, sweeping highlight, flickering grid, animated aura, cursor trail, typing keyboard, and pulsing indicators.
- Evidence: `frontend/app/block/block.scss:175-220` applies the layered glow and endless scan; `frontend/app/block/blockframe.tsx:215-244` mounts the flickering grid, aura, cursor, and keyboard together; `frontend/app/block/agent-aura.scss:212-232` loops the aura; `frontend/app/block/typing-keyboard.scss:42-60` adds another blurred glowing loop.
- Additional issue: `frontend/app/block/agent-aura.scss:67-75` disables `.agent-aura`, but the rendered class is `.agent-widget-aura`, so reduced-motion mode does not stop the main aura. The glow and scan in `block.scss` and keyboard loop also have no local reduced-motion override.
- Proposed fix boundary: choose one persistent activity signal, use short event animations only for discrete cursor or typing events, remove the rainbow scan and decorative flicker, and make reduced motion stop all nonessential loops.

### 5. [MEDIUM] Glass and elevation are default chrome, not selective hierarchy

- Rules: R-10, glass dose cap; R-12, selective elevation.
- One-line reason: blur, gradient, border, and large shadow recur across navigation, layout controls, popovers, and web controls, so opening one overlay can place several frosted elevated layers on screen.
- Evidence: `frontend/app/tab/tabbar.scss:4-29` blurs and gradients the top bar; `frontend/app/tab/vtabbar.scss:4-12` does the same to vertical navigation; `frontend/app/tab/workspace-presentation-switcher.scss:12-63` applies blur and shadow to both trigger and popover; `frontend/app/workspace/web-mode.scss:74-115` adds another blurred capsule and large elevated panel.
- Proposed fix boundary: keep one elevated overlay treatment for menus and dialogs, make persistent navigation matte, remove shadows from non-overlays, and let borders and surface tone carry the workspace hierarchy.

### 6. [MEDIUM] Kronarchy mode uses the generic gradient-and-orb stack

- Rules: R-01, color and gradients need purpose; R-07, background texture needs identity purpose.
- One-line reason: the mode applies two linear gradients plus a bottom radial glow to the entire body, producing the stock dark blue-purple atmospheric background called out by the anti-slop rules.
- Evidence: `frontend/app/workspace/kronarchy-shell.scss:616-633` defines the fixed three-gradient body background; `frontend/app/workspace/kronarchy-shell.scss:792-803` repeats a similar gradient stack for canvas, though canvas is outside this audit's primary scope.
- Proposed fix boundary: make the non-canvas shell a solid or lightly tonal work surface and reserve any glow for a single meaningful state, not the workspace backdrop.

### 7. [MEDIUM] Wide-tracked uppercase micro-labels have become the default typographic voice

- Rule: R-06, typography needs a brand and readability reason.
- One-line reason: tiny uppercase, wide-tracked headings repeat across every navigation and launcher surface, which reads as generic technical styling and reduces scanability.
- Evidence: `frontend/app/workspace/widgets.scss:13-20`, `194-205`, `649-655`, and `711-718`; `frontend/app/tab/vtabbar.scss:183-191` and `247-257`; `frontend/app/tab/workspace-presentation-switcher.scss:110-123`; `frontend/app/workspace/kronarchy-shell.scss:396-403`.
- Proposed fix boundary: use sentence case for section names, keep one compact typographic convention for true metadata, and increase small-label size or contrast where it carries navigation meaning.

### 8. [MEDIUM] The active palette fragments into unrelated accent systems

- Rules: R-01, purposeful color; R-29, restrained palette.
- One-line reason: shared workspace chrome mixes the theme accent with Saturn gold, hard-coded blue and indigo agent colors, emerald status, and per-app white defaults instead of one semantic token system.
- Evidence: `frontend/app/block/agent-aura.scss:7-12` introduces agent blue; `frontend/app/block/agent-aura.scss:34-64` alternates blue and indigo; `frontend/app/block/typing-keyboard.scss:33-59` introduces gold; `frontend/app/tab/tabbar.scss:128-135` uses `--color-saturn`; `frontend/app/tab/widget-tabs-layout.scss:521-531` hard-codes green; `frontend/app/workspace/widgets.tsx:532-546` defaults app icon color to white.
- Proposed fix boundary: map focus, agent-active, success, warning, and neutral states to shared semantic tokens; remove component-local brand colors; allow app-owned colors only when supplied by real app metadata.

### 9. [MEDIUM] Generic AI and placeholder icons are used as product identity

- Rule: R-04, relevant icons with a stated purpose.
- One-line reason: the Kronos surface is represented by the generic robot glyph and missing app identities fall back to the same cube, making unrelated actions look generated from a default icon vocabulary.
- Evidence: `frontend/app/workspace/kronarchy-shell.tsx:276-281` uses `fa-robot` for Kronos; `frontend/app/workspace/widgets.tsx:477-482`, `503-513`, and `532-546` use `cube` as the repeated fallback.
- Proposed fix boundary: use a product-specific existing Kronos mark if one is already approved, otherwise use a neutral window/app glyph; use type-specific fallbacks for terminal, browser, file, desktop app, and extension instead of one cube.

### 10. [LOW] The workspace has competing style systems instead of one documented desktop identity

- Rules: R-20, visual identity; R-30, do not clone; R-31, major decisions need reasons.
- One-line reason: the default shell uses rounded Hermes surfaces while Kronarchy replaces them with square Tokyo Night chrome and explicitly describes itself as Omarchy-inspired, with no root design source explaining when either language is the product.
- Evidence: `frontend/app/workspace/workspace-appearance.ts:17-35` defines Hermes, mono, and system font modes; `frontend/app/workspace/kronarchy-shell.scss:542-615` replaces the complete token set and radii; `frontend/app/workspace/kronarchy-shell.tsx:244-247` says `Omarchy-style`; `frontend/app/workspace/kronarchy-shell.tsx:299-303` says `Omarchy-inspired`.
- Proposed fix boundary: document one KronTerm desktop direction, make widgets and tabs share it, and treat density or chrome variants as controlled adjustments rather than separate borrowed identities.
