# Review 32: MCP schema and tool error contracts

Priority: P2. Preserve explicit failure independently of message truthiness in `normalizeToolResult`.

## Observed finding

At `/Users/albsheralsadi/kronterm/mcp-kron-term/src/tool-execution.ts:41`, an explicit `success: false` assigns the error/message value to `failure`. Lines 46-47 do the same for JSON text containing `success: false` or `met: false`. Line 52 then uses the truthiness of that value to decide whether to set `isError`. Consequently, `{success:false,message:""}` and a text block containing `{success:false,error:""}` both leave `isError` unset. These are observed results from direct imports through `node --import tsx`, not an inferred SDK behavior. Multiple text blocks can also overwrite an earlier nonempty failure with an empty message.

The normalizer is called before `executeTool` attaches failure metadata; the latter treats an unset `isError` as success for diagnostics. An upstream explicit failure with an empty message therefore bypasses both MCP failure classification and the structured recovery contract. Whether any current bridge produces these exact payloads is unverified; the demonstrable defect is in the shared contract and has bounded edge-case scope.

## Proposed change and acceptance criteria

Track a monotonic failure boolean separately from message content. Preserve existing explicit `isError` results and plain successful text. Avoid imposing new schemas on arbitrary text blocks as part of this fix.

Acceptance: direct and embedded `success:false` payloads remain errors with empty error/message values; embedded `met:false` behaves identically; later content cannot erase an earlier failure; `executeTool` emits `ACTION_FAILED` metadata and error diagnostics for these cases. Cover the exact edge cases in `test/tool-execution.test.ts`, including multiple blocks. Keep successful plain text and existing timeout/cancellation cases green.
